Gateway Configuration: MultiTech Conduit

Oct 27, 2026. What we set up on the bench gateway today, why, and how to check it.

The big picture

A gateway never makes ADR decisions itself; the network server it feeds does. Our MultiTech Conduit can either run its own built-in network server or forward every packet to an outside one. That one setting decides which ADR algorithm drives our board.

The board, the radio and the channels stay the same in both modes; only the ADR decision maker changes. That is the stakeholder's situation in miniature: one firmware, two network servers, different behaviour.

Bench network

The gateway came with a fixed address, 192.168.137.2, that the workstation could not reach. We made it a DHCP client on the office LAN, so it now behaves like any other host there.

We chose LAN + DHCP client rather than WAN because the gateway's remote-access settings allow the web UI and SSH on LAN ports only; WAN would have meant opening them up.

How AEP applies a change

AEP's web UI is a thin layer over a local REST API, and our scripts call the same API. A change is staged in memory and only becomes permanent with save_restart, which saves it and reboots the gateway.

What we sawCauseFix
404 "data not found"PUT of a partial element, or of a whole collectionGET the element, change it, PUT it back whole
417 Expectation Failedcurl sends Expect: 100-continue with larger bodies; the old web server refuses itadd -H 'Expect:'
411 Length RequiredPOST with no body at alladd -d ''
save_apply not foundAEP 1.7.4 only has save and save_restartuse save_restart

On the gateway itself, http://127.0.0.1/api answers without a login. AEP's own boot scripts read it that way, and so does our watch-board.py.

LoRa modes

TermWhat it means
Packet forwarderlora_pkt_fwd, running in both modes. It takes packets from the LoRa card and sends them to a network server over Semtech UDP, and transmits the downlinks it gets back.
Built-in network serverlora-network-server, MultiTech's own LoRaWAN server inside AEP. In network server mode the forwarder talks to it locally, on 127.0.0.1 ports 1780 and 1782. (ADR)
Network server modeAEP setting packetForwarderMode = false. Joins, keys and ADR are all handled on the gateway. Our setup today.
Packet forwarder modepacketForwarderMode = true. The built-in server stops; packets go to serverAddress on UDP 1700, which will be our ChirpStack.
Semtech UDPThe original gateway-to-server protocol: JSON over UDP port 1700, unencrypted. ChirpStack's gateway bridge speaks it.
Gateway EUIThe gateway's 64-bit ID, sent with every packet: 00800000A00006DD, set at the factory on the LoRa card. ChirpStack must be given exactly this value.

At boot in packet forwarder mode, AEP's start-up script (/etc/init.d/lora-network-server, read on the gateway today):

  1. reads the LoRa settings from the local API;
  2. runs the network server once, only to generate the radio configuration;
  3. writes the server address and ports into /var/run/lora/*.json;
  4. starts the packet forwarder.

Radio channels: sub-band 2

An 8-channel gateway hears one AU915 sub-band only. Gateway, network server and board must all use the same one, or uplinks are lost without any error message.

WhereSettingValue
Gateway, network serverlora.frequencySubBand2: channels 8-15 + 65
Gateway, packet forwarderpacketForwarder.frequencySubBandwas 1 (channels 0-7); conduit-lora-mode.sh forwarder sets 2
Our ChirpStackenabled_regionsau915_1 (916.8 MHz and up)
Board firmwaresub-band, channel mask2, FF00.0000.0000.0000.0002

Today's catch: the forwarder section was still on sub-band 1. Switching modes without fixing it would have made the gateway deaf to our board. ChirpStack's au915_0 region is sub-band 1 too (it starts at 915.2 MHz), so which region the stakeholder's ChirpStack uses is worth asking.

ADR on our board today

With the built-in server in charge, our board has been moved to DR3 and TX power index 10.

The built-in server has already walked our board onto the low-power amplifier, and the board keeps working because the Nucleo wires both amplifiers. ChirpStack's default ADR goes further and faster, down to index 14 (see the primer, hypothesis 1).

Next: hand ADR to ChirpStack

  1. register-gateway.sh add and register-device.sh add (local ChirpStack only).
  2. conduit-lora-mode.sh forwarder: the gateway reboots, 2-3 min.
  3. conduit-lora-mode.sh status, then register-gateway.sh status: the gateway should show as seen. That also proves UDP 1700 gets through the workstation firewall.
  4. Reset the board and watch its trace for a Join-Accept from ChirpStack.

From then on it is the same board, gateway and radio with ChirpStack's ADR in charge: the comparison the stakeholder is asking about.
