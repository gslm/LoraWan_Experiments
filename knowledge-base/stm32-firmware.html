STM32 Firmware: the LoRaWAN End Node on Our Nucleo

Oct 27, 2026. How the board was flashed and how its firmware is put together. Built from firmware/README.md and the project source.

The big picture

Our board runs ST's own LoRaWAN_End_Node example from STM32CubeWL v1.4.0, the same LoRaWAN stack family the stakeholder uses. We changed three things: lab settings (AU915 sub-band 2, a 15 s period), a detailed ADR trace, and a self-contained build.

Nothing on the board is custom LoRaWAN code: every ADR decision it executes goes through ST's unmodified logic. The trace only reads state.

The hardware link

The ST-LINK is a second small chip on the Nucleo. It turns USB into the chip's debug port (SWD) and into a serial port, so one cable flashes the board, shows its trace and powers it.

Building and flashing, step by step

Build with ST's GCC 14.3 (the same compiler the STM32 VS Code extension uses):

# workstation
cd /media/guilhermes/ssd/LoraWan_Experiments/firmware/LoRaWAN_End_Node_ADR
export PATH=$HOME/.local/share/stm32cube/bundles/gnu-tools-for-stm32/14.3.1+st.2/bin:$PATH
cmake --preset Debug
cmake --build --preset Debug

This produces build/Debug/LoRaWAN_End_Node_ADR.elf. Flash it through the ST-LINK:

# workstation
cd /media/guilhermes/ssd/LoraWan_Experiments/firmware/LoRaWAN_End_Node_ADR
PROG=~/.local/share/stm32cube/bundles/programmer/2.23.0/bin/STM32_Programmer_CLI
$PROG -c port=SWD sn=003F00223431511931343632 mode=UR -e all -d build/Debug/LoRaWAN_End_Node_ADR.elf -v -rst
OptionWhat it does
-c port=SWDconnect through the ST-LINK's SWD debug lines
sn=003F...3632pick this ST-LINK by serial number (safe with several boards plugged in)
mode=URconnect under reset: works even if the running firmware sleeps or turns debug off
-e allerase the whole flash first, including an old NVM context at 0x0803F000
-d <file>.elfdownload the firmware; the addresses come from the .elf file
-vread the flash back and verify it
-rstreset the chip so the new firmware starts

Then watch the trace (Ctrl-A Ctrl-X exits picocom):

# workstation
cd /media/guilhermes/ssd/LoraWan_Experiments/firmware
picocom -b 115200 /dev/ttyACM2

Before the very first flash, the teammate's demo (a Zephyr application) was read out of the board twice, the two copies were checked identical, and the image was kept in firmware/backup/ with its SHA-256. firmware/README.md section 9 has the one command that puts it back.

Project layout

The only ST stack files we touched are LoRaMac.c and LoRaMacCommands.c, and only to add trace calls. Every change is marked LAB: or ADR-TRACE and collected in patches/adr-trace.diff.

Software layers

ADR is executed in the two blue layers: LoRaMac receives the LinkADRReq and the AU915 region code decides whether it can be applied. The board file at the bottom decides which amplifier actually drives the antenna, which is why it is the first file to ask the stakeholder for.

The ADR trace

TagWhen it appearsWhat it tells you
[JOIN]at boot and during the joinconfiguration, JoinRequest (DevNonce, channel, DR), Join-Accept (DevAddr, RX settings), result
[UL]every transmission, then a "done" lineframe counter, channel, DR, TX power index, real radio output (HP/LP, clamped), ADR bits
[DL]every accepted or dropped downlinkwindow (RX1/RX2), RSSI, SNR, port, ACK, ADR_ACK_CNT reset
[MAC]when MAC commands arrive or answers are queuedevery command decoded, and every answer the device will send
[ADR]after a LinkADRReq block, or a device back-off stepAPPLIED or REJECTED, with old and new DR, power, NbTrans and channel mask

Example: the first ADR exchange after the join

[DL] t=48.440 RX1 DR10(SF10/500) rssi=-52 snr=7 CONF FCntDown=1 DevAddr=0146BD4D FPort=0 FRMPayload=10B FOptsLen=0 ACK=0 ADR=0 FPending=0 ADR_ACK_CNT=0->0
[MAC] t=48.441 RX 10 byte(s) of MAC commands in RX1 (snr=7), 2 parsable cmd(s): 0320020071032000FF01
[MAC] t=48.441   LinkADRReq [block 1, cmd 1/2] raw=0320020071 DataRate=DR2(SF10/125) TXPower=0(EIRP 30.0dBm) ChMask=0x0002 ChMaskCntl=7 NbTrans=1
[MAC] t=48.441   LinkADRReq [block 1, cmd 2/2] raw=032000FF01 DataRate=DR2(SF10/125) TXPower=0(EIRP 30.0dBm) ChMask=0xFF00 ChMaskCntl=0 NbTrans=1
[ADR] t=48.442 LinkADRReq block of 2 cmd(s) -> LinkADRAns status=0x07 (PowerACK=1 DataRateACK=1 ChMaskACK=1) x2 => APPLIED: DR2(SF10/125)->DR2(SF10/125) TXPower 0->0 NbTrans 1->1 ChMask(now)=FF00.0000.0000.0000.0002 ch=8-15,65
[MAC] t=48.442 queue LinkADRAns (CID 0x03) payload=07 [PowerACK=1 DataRateACK=1 ChMaskACK=1]
[UL] t=48.449 FCnt=2 UNCONF port=0 len=4 tx=1/1 ch=12 f=917.600MHz DR2(SF10/125) pwr=idx0 EIRP=30.0dBm cond=27dBm rf=22dBm(HP,CLAMPED) ToA=330ms ADR=1 ADRACKReq=0 ACK=1 ADR_ACK_CNT=0/64+32 ULdwell=1
LineWhat happened
[DL]A confirmed downlink arrived in RX1 on port 0, so its payload is MAC commands only (10 bytes).
[MAC] RXThe 10 bytes hold two commands: 03 20 02 00 71 and 03 20 00 FF 01.
[MAC] cmd 1/2LinkADRReq with ChMaskCntl 7: all 125 kHz channels off, mask 0x0002 turns on 500 kHz channel 65.
[MAC] cmd 2/2LinkADRReq with ChMaskCntl 0, mask 0xFF00: channels 8-15 on. DR2, TX index 0, NbTrans 1.
[ADR]The block passed all three checks (status 0x07) and was applied as one unit: sub-band 2 plus channel 65.
[MAC] queueThe answer LinkADRAns 0x07 is queued for the next uplink.
[UL]Because the downlink was confirmed, the board answered at once on port 0 with ACK=1. Note rf=22dBm(HP,CLAMPED): index 0 asks for 27 dBm, the chip gives 22.

What this means for the stakeholder

  • Same stack family. Our MW 2.6.2 is the newest LoRaMac-node based release; the stakeholder's boot banner tells us how far they are from it.
  • The board file matters most. Our Nucleo wires both amplifiers. A module that wires only the HP amplifier, built with the Nucleo's board file, loses every uplink at TX index 6 and above.
  • DevNonce must survive resets. ST's example saves it only when B3 is pressed; LoRaWAN 1.0.4 forbids reusing it, so a product must save it itself.
  • Dwell time is on at boot in AU915. The lowest uplink DR is DR2, which carries at most 11 bytes until a server sends TxParamSetupReq.
